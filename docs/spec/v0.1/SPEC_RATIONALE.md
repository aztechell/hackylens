# Requirement audit for Architecture Specification v0.1

This audit refers to the normative statements in [Architecture](README.md) and
[Services](SERVICES.md) as merged at
[`7d3e7db`](https://github.com/aztechell/hackylens/commit/7d3e7dbfc94ded50e40af0d35dd226b14286fca5).
The linked ID supplies the normative text. Each evidence column specifies an
observation to obtain. The [matrix](requirements.csv) links IDs to scenarios in
the [conformance plan](CONFORMANCE.md). Scenario assignment records intended
coverage. A result must identify the observations it actually supplies.

## Profile boundaries reviewed

| Requirement | Audit decision for v0.1 | Scope of the resulting claim |
| --- | --- | --- |
| CMP-01 | Retain static, immutable native composition for this candidate. Freezing the eligible set before execution lets operators audit capability availability and capacity without a loader or changes to persisted identity. | Build-time generation and a validated fixed image table are both viable. A runtime that changes the eligible set after execution begins needs a distinct contract for admission and compatibility. |
| LIF-01 | Retain one foreground native instance. It defines observable ordering when a foreground application changes and gives release of foreground resources a single transition. | The rule applies to the foreground slot. Persistent services and workers may have separate lifecycles. Multiple concurrent foreground slots would require explicit routing, arbitration and ordering rules. |
| LIF-02 | Retain synchronous and serialized lifecycle callbacks for this profile. A terminal callback result gives the runtime a definite point to handle errors and phase transitions. | A dispatcher may use an executor or an isolated task while preserving the synchronous boundary and serial order. Deferred operations have their own lifetime. Runtime budgets require evidence about finite work and observed violations. |

These choices define the class of systems evaluated in v0.1. An alternative
mechanism in the tables is illustrative and still subject to the normative
conditions. The audit records no normative revision.

## Core

| Requirement | Concern | Rationale | Permitted mechanisms | Required evidence |
| --- | --- | --- | --- | --- |
| [ARC-01](README.md#architecture) | Scope and reproducibility | A claim needs an explicit configuration and constraints so a third party can determine applicability and reproduce results. | A retained build manifest or an inspectable configuration declaration. | Review the declaration against the tested image/configuration and check all required fields, including limits, policies and binding versions. |
| [ARC-02](README.md#architecture) | Dependency direction | A typed boundary preserves substitutions across implementations and keeps provider behavior free of app or language policy. | Direct typed calls, vtables or typed messages across an IPC boundary. | Review build dependencies and published interfaces for app/adapter access and provider reverse dependencies. A trace can corroborate routing, while boundary completeness requires structural review. |
| [ARC-03](README.md#architecture) | Finite resource use | Declared capacities make overload explicit and permit a memory budget before a run. | Fixed arrays, partitioned arenas or preallocated slabs, including a separately budgeted script heap. | Review allocations against the declared limits. Exhaust each bounded pool and repeat runs, observing explicit exhaustion and no growth of retained run-owned state. |
| [ARC-04](README.md#architecture) | Arbitration | One authoritative decision path prevents incompatible clients from independently granting access to the same resource. | One executor, one locked provider or one serialized device command queue. | Review all entry paths and provoke competing requests across clients. Confirm serialized authority and side effects only from the authorized path. |
| [CMP-01](README.md#composition) | Reproducible admission | A fixed eligible set, stable identity and finite descriptors bound and make selection auditable. | Generated registry or immutable image table with explicit IDs. | Inspect registry and descriptors, compare identities after reordering, and demonstrate registry immutability during execution. |
| [CMP-02](README.md#composition) | Invalid and unavailable apps | Early rejection avoids ambiguous identity and impossible launches, while optional absence has predictable behavior. | Link/build validation plus generated selection, or separate build-time validation and a validated fixed table. | Submit invalid and duplicate IDs, absent required and optional services, and an explicitly required app with a missing dependency. Observe rejection, omission, fallback and no acquisition as applicable. |
| [CMP-03](README.md#composition) | Stable selection and persistence | Build order and disablement must preserve the meaning of saved app references. | Deterministic table ordering or stable-key comparison and reservation of the disabled app's identity. | Compare equivalent, reordered configurations semantically. Disable one app and confirm its persisted ID never selects another app. |
| [LIF-01](README.md#lifecycle) | Instance isolation | Ordered admission prevents two foreground instances from acting on the same slot and keeps residual state out of a new launch. | One reusable slot or separate storage with a unique foreground admission gate. | Launch A with nonzero prior state and switch to B. Check validation, zeroed declared state, fresh identities, scope preparation before start and full A retirement before B admission. |
| [LIF-02](README.md#lifecycle) | Callback ordering and bounded work | Serialized terminal callbacks let state transitions and failure attribution follow one observable order. | Cooperative loop or executor with a synchronous callback boundary. | Observe callback entry/return and teardown acceptance while injecting reentrant or competing dispatch. Check phase, overlap, terminal results and finite work assumptions. |
| [LIF-03](README.md#lifecycle) | Event integrity and close semantics | Sequence and timestamps preserve ordering and make bounded queues and closure deterministic from a client's perspective. | Bounded queue or bounded serialized event delivery with per-instance sequence. | Observe increasing nonzero sequences and monotonic timestamps for accepted input/timer/close, including pressure. Exercise app requests, external close during start, and Back as normal input where supported. |
| [LIF-04](README.md#lifecycle) | Timer cadence | Rescheduling from observed start prevents bursts after delay and separates callback cadence from work budget. | Polled timer or an underlying alarm with equivalent scheduling and accounting. | Control the clock, miss multiple periods and vary cadence and budget independently. Check scheduled/observed timestamps and inject budget excess, clock failure and arithmetic overflow. |
| [LIF-05](README.md#lifecycle) | Terminal notification | A running event surface gets a single logical close signal before stop, even when a callback fails. | Dispatcher-synthesized close event or an equivalent serialized internal dispatch. | Count and order runtime-close and stop after ordinary close and terminal callback errors. Exercise failure of runtime-close itself and paths that never enter the running event surface. |
| [LIF-06](README.md#lifecycle) | Partial startup unwind | Cleanup obligations follow actual initialization progress so each initialized stage can be retired safely. | Recorded phase flags or a bounded ownership ledger. | Inject validation, partial preparation and start failures. Count stop and retirement at each phase and verify repeating stop is safe in the callback contract. |
| [LIF-07](README.md#lifecycle) | End-to-end teardown budget | A single deadline bounds the budget supplied to every participant and blocks extension through retries or handoff. | Pass an absolute value explicitly or carry it in a runtime-owned close context. | Observe the absolute deadline at stop and every retirement with delayed and failing clocks. Verify continued logical cleanup after expiry and rejection of scoped acquisition. |
| [LIF-08](README.md#lifecycle) | Safe reuse after failures | Ordered best-effort unwind prevents leaked authority and avoids reuse of storage while an old worker can reach it. | Fixed retirement slots, a tracked resource ledger or fail-closed disabled storage. | Inject stop and retirement errors and identity exhaustion. Observe all retirement attempts, quarantine, token and context invalidation, state release when safe, and unaffected provider access. |
| [LIF-09](README.md#lifecycle) | Deferred work identity | Old work reaching a new instance can mutate state or deliver spurious events unless validated before effects. | Epoch plus operation ID, or a reserved non-reusable handle namespace. | Hold work across switch and reuse, then deliver old and wrong-operation completions. Accelerate identity exhaustion and check that stale completions produce neither a callback nor a state change. |
| [OWN-01](README.md#ownership) | Resource conflict semantics | Explicit claim granularity and context let clients know which resource is reserved and what a failed attempt changed. | Resource bitmap, fixed claim slots or immutable read-only bindings. | Review each service contract. Attempt overlapping or invalid multi-resource claims and confirm atomic failure by querying unaffected state and exercising later claims. |
| [OWN-02](README.md#ownership) | Authority aliasing | Copy and reuse must preserve the single owner's authority and callback lifetime limits. | Address-registered sessions or an opaque capability tied to authenticated caller/context. | Copy a handle or hold context and render references past the callback. Use the copies from wrong and later contexts and compare provider state/effects with the pre-call state. |
| [OWN-03](README.md#ownership) | Buffer safety | A cancellation request may leave active access. Explicit bounds and lifetime prevent collisions between producers and borrowers. | Synchronous borrowing, explicit terminal acknowledgment or separately owned staging storage. | Audit buffer declarations and hold a producer across cancel or timeout. Observe access until quiescence, then attempt buffer reuse and check capacity, permissions and layout constraints. |
| [OWN-04](README.md#ownership) | Unsafe retirement | Forced logical revocation removes old authority even when a device cannot yet be brought to a safe state. | Local quarantine, disable-until-reset or release after a documented quiescence acknowledgment. | Fail ordinary close to exercise retry. Fail forced retirement, then observe rejection of old authority and every reuse attempt before the documented safe boundary. |
| [OWN-05](README.md#ownership) | Scope separation | Closing a launcher or a run should affect only the resources it is authorized to retire. | Distinct scope identities with provider-side records or independent runtime-owned ledgers. | Acquire resources in persistent, instance and script scopes. Close each applicable scope and observe surviving resources and retirement driven by authoritative records. |
| [TIM-01](README.md#time-and-errors) | Shared time domain | Common monotonic time makes deadline comparisons meaningful across clients, providers and callbacks. | Hardware counter conversion or a scheduler clock with checked conversion and wrap handling. | Compare runtime and service observations against one clock source. Inject invalid/regressing time and arithmetic overflow, and distinguish immediate expiry from any unbounded sentinel. |
| [TIM-02](README.md#time-and-errors) | Deadline propagation | Retrying or routing a call cannot silently increase the caller's budget. | Forward a deadline in an immutable request, or carry it in synchronized operation state. | Trace the same value across retries, transfers and cleanup. Exercise documented cancel/expiry ordering and compare check intervals with their declared limits. |
| [TIM-03](README.md#time-and-errors) | Progress and expiry | Clients need a terminal result or recovery path, with tightly bounded safety work after expiry. | Bounded polling steps, finite blocking primitives or a documented escalation path. | Delay or stall operations. Observe terminal/recovery behavior and audit blocking bounds. Inspect hardware effects after expiry and confirm logical retirement still runs. |
| [ERR-01](README.md#time-and-errors) | Distinguishable outcomes | Stable outcome categories support portable callers and make validation failures distinguishable from failure after effects. | Result enum, typed tagged result or exception mapping that preserves categories. | Exercise the relevant error categories including version incompatibility where supported. Observe output and provider effects before and after validation failures. |
| [ERR-02](README.md#time-and-errors) | Failure attribution | Preserving the first terminal failure supports diagnosis while allowing cleanup of remaining resources. | First-error slot plus cleanup diagnostics, or a result with the primary error and secondary details. | Inject distinct initial and cleanup errors. Verify the first survives, subsequent cleanup is attempted and non-success outputs follow the operation contract. |

## Shared Script and Recovery

| Requirement | Concern | Rationale | Permitted mechanisms | Required evidence |
| --- | --- | --- | --- | --- |
| [SCR-01](README.md#shared-script) | Native/script parity | Common service authority keeps conversions, conflicts and outcomes consistent across execution models. | In-process typed bindings or serialized cross-context bindings to the same provider. | Run equivalent operations and mixed-client conflicts, compare normalized values and errors, and review that both paths reach the same production provider. |
| [SCR-02](README.md#shared-script) | Engine fit and isolation | Bounded memory and work and a distinct run identity keep interpreter activity within its declared scope. | Dedicated heap or budgeted fixed arena and an explicit run state machine. | Review the interface and declared budgets. Reach memory and work capacity and attempt a conflicting run. Check outcomes, run identity and residual ownership after repetition. |
| [SCR-03](README.md#shared-script) | Request handoff safety | Explicit synchronized request ownership prevents in-flight storage reuse and mismatched results under cancellation. | Bounded queue, fixed-slot mailbox or direct calls on one serialized context. | Stall a consumer, saturate the handoff and cancel. Check storage ownership and result identity until terminal release. Review synchronization for each crossing if present. |
| [SCR-04](README.md#shared-script) | Cooperative stop | An acknowledgment can precede worker quiescence. A finite mode and stop gate prevent admitting new work into a stopping run. | VM checkpoints, bounded task steps or cancellation checks at service boundaries. | Stop and expire running scripts, defer the worker terminal handoff and verify no new admission or reuse during the gap. |
| [SCR-05](README.md#shared-script) | Terminal convergence | Exit, failure and launcher closure must preserve worker storage until the run retires or enters a fault state. | Common teardown path plus a non-reusable fault state, or independent recovery when declared. | Trace exit, exception, stop, expiry, launcher close and intentional non-cooperation. Verify terminal cleanup, or observe the declared non-reusable or recovery state. |
| [REC-01](README.md#recovery) | Independent escalation | A stalled worker cannot be trusted to execute its own recovery path. | Independently scheduled supervisor or hardware watchdog, within the documented reset scope. | Inject physical non-cooperation. Capture trigger, grace and escalation from an independent observation and compare observed scope and configured bounds. |
| [REC-02](README.md#recovery) | Safe restart and persistent data | Suppressing the offending autostart avoids restarting a fault loop while preserving the user's committed state. | Boot flags and autostart gate, or a durable fault marker read at restart. | Observe recovery cause and suppression. Compare supported committed program/settings evidence before and after, and check recovery policy for deliberate erase. |

## Services

Time is part of Core. The remaining rows apply to the corresponding declared
extension. Each service also inherits the applicable common contracts.

| Requirement | Concern | Rationale | Permitted mechanisms | Required evidence |
| --- | --- | --- | --- | --- |
| [S-TIME-01](SERVICES.md) | Portable clock and sleep | Separating a wake target and a deadline makes sleep races and clocks with no progress observable. | Polled bounded slices or an interrupt-backed wait with equivalent precedence. | Set target, cancel and expiry at equal or distinct times. Exercise progress, frozen/regressing clock, maximum interval, overflow and declared check slices. |
| [S-INPUT-01](SERVICES.md) | Shared logical transitions | Uniform masks, sequence and acceptance time let clients reconstruct transitions without guessing at hardware behavior. | Debounced polling or interrupts normalized by a single state machine. | Feed transitions, held and supported pulse-only inputs according to the declared sampling policy. Compare masks, sequence and timestamps across clients. |
| [S-INPUT-02](SERVICES.md) | Independent event consumption | One reader's progress must preserve another reader's history up to the declared finite capacity. | Bounded ring with cursors or an equivalent fixed history with independent read positions. | Open two readers before traffic. Check non-consuming state reads, pending empty reads, exact loss, resync and independence after one close. |
| [S-LIGHT-01](SERVICES.md) | Atomic channel authority | Overlap rejection and effects-free validation protect unrelated channels and permit disjoint clients. | Channel bitset or owner per channel with a transactional validation step. | Try valid, overlapping, empty, unsupported and unauthorized channels plus out-of-range values. Record peer claims and output effects. |
| [S-LIGHT-02](SERVICES.md) | Bounded safe-off | Retryable ordinary close and forced invalidation have different consequences for authority and reuse. | Per-channel retirement with local quarantine, or an equivalent safe-off controller. | Inject per-channel failure and expiry. Observe safe-off attempts, retained retryable claim, unchanged deadline, invalidation and local quarantine. |
| [S-DISP-01](SERVICES.md) | Portable geometry | Uniform clipping and pixel interpretation allow the same output across display implementations. | Hardware or software clipping, framebuffer or bounded streaming. | Review declarations and compare pixel/transaction traces for overflow, no-op regions, partial stride and clamping, null clip, color byte order where supported and claim conflicts. |
| [S-DISP-02](SERVICES.md) | Transaction and borrow safety | Terminal operations give a definite end to writable access and preserve staged output after validation errors. | Staged frame, transaction buffer or bounded command queue. | Exercise begin, modes and invalid mixing, invalid commands, present/abort and failed retirement. Check staged contents, stale borrows and reuse. |
| [S-RENDER-01](SERVICES.md) | Runtime render authority | A callback gets a bounded drawing surface while the runtime retains transaction completion and failure cleanup. | Runtime-issued render borrow over a typed display service. | Try prohibited app actions, busy display and render/provider/present/budget failures. Trace attempts, abort, retained invalidation and unwind. |
| [S-RENDER-02](SERVICES.md) | Bounded redraw scheduling | Coalescing preserves redraw work without unbounded accumulation and makes in-render requests observable. | Fixed rectangle set with full-redraw fallback or equivalent bounded representation. | Start with and without render, repeat and exceed invalidation capacity, invalidate during render and request outside RUNNING. Observe resulting future passes and explicit failures. |
| [S-LINK-01](SERVICES.md) | Shared connector arbitration | A connector cannot switch electrical routing during an owned transfer without risking conflicts. | One connector lease and typed per-mode adapters with serialized reconfiguration. | With an external peer where needed, claim overlapping modes, attempt invalid and active switches and observe routing and quiescence. |
| [S-LINK-02](SERVICES.md) | Transfer lifetime | Partial progress and stale tokens must remain distinct across reopen and cancellation. | Bounded DMA with explicit quiescence or incremental interrupt/polled transfers. | Inject partial transfer, expiry, cancellation and ordinary/forced close failures. Observe absolute deadline, progress, stale-token outcomes and buffer access until quiescence. |
| [S-POWER-01](SERVICES.md) | Coordinated power transition | Hardware action should follow successful bounded preparation, with restoration where a failed action returns. | Ordered preparation state machine or synchronous finite steps with rollback where supported. | Exercise unsupported, pending, expired and failed actions. Trace script/storage steps, power action suppression and mount restoration when applicable. |
| [S-ACCEL-01](SERVICES.md) | Portable sample semantics | Consistent signed units and output validity prevent consumers from using partial or stale samples as successful reads. | Sensor-specific conversion into declared axes and units. | Check known signed samples and absent, settling, I/O and unsupported paths. Sentinel outputs must survive failed reads. Review motion status when supported. |

## Applying the audit

Each evidence criterion may combine structural review, host observations and
target observations. For example, a trace can show stale-token rejection and
recorded cleanup order. Allocation bounds, all dependency paths and physical
quiescence require additional evidence. Cases shared across several rows may
satisfy only some of their criteria in a given run.
